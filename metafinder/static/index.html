How to make a game compatible

A compatible game ships a headless rules module in Python: no graphics, input, sound, network or clocks. MetaFinder imports it into its own process and calls it hundreds of thousands of times per run, so the rules have to be fast and in-process.

Languages

Game written inSupported?
Python 3.10+, standard library onlyYes, the intended case
Python + third-party packages (numpy, pygame…)Only if MetaFinder's environment already has them. Your requirements.txt is not installed.
pygame / arcade / Ren'Py gamesYes, if the rules are separate from the game loop (no window, input or sleep)
Compiled extensions (Cython, PyO3…), or C/C++/Rust via ctypesOnly with a committed prebuilt binary for this OS, CPU and Python version. Nothing is built.
JS/TS, C# (Unity), GDScript (Godot), Lua, Java…No. Port the rules (not the UI) to Python. Subprocess or HTTP wrappers are far too slow.

The clone is shallow (--depth 1). Git submodules and Git LFS files are not fetched.

Layout

my-game/                        ← repo root, or the folder you link with /tree/<branch>/<path>
├── metafinder.json             ← { "entry": "my_game.metafinder_adapter:GAME",
│                                   "config": { "starting_hp": 20 } }
├── my_game/
│   ├── __init__.py
│   ├── rules.py                ← pure logic, no UI imports
│   └── metafinder_adapter.py   ← defines GAME
└── ui/, assets/ …              ← ignored

entry is module.path:attr, relative to that folder (attr defaults to GAME; a class or factory gets called). config is passed to new_game, and the config box here overrides it. Shortcut: a metafinder_game.py defining GAME. Don't name your package metafinder or shadow stdlib modules.

Game object

name, num_players, perfect_information               required
new_game(seed, config) -> State                     required; setup randomness from seed only
max_steps = 500                                     optional cap on actions per game
rollout_depth                                       optional; playouts stop here and use heuristic_value()
default_rollout_policy(state, rng) -> action        optional, smarter playouts

State object

clone()            -> fully independent copy, and FAST (avoid copy.deepcopy)
current_player()   -> 0..n-1, or -1 for a chance node (draws, dice, shuffles)
legal_actions()    -> non-empty list, no duplicates, deterministic order
apply(action)      -> mutate in place, deterministically
is_terminal()      -> bool
returns()          -> one value per player in 0..1 (1 win, 0 loss, 0.5 draw)

chance_outcomes()  -> [(outcome, probability)] summing to 1   if current_player() can be -1
determinize(observer, rng) -> NEW state                        if perfect_information is False
                      re-randomize only what observer can't see; keep their legal actions
to_json()          -> complete state as JSON (strongly recommended: powers the checks)
heuristic_value()  -> like returns(), for unfinished games
describe(), action_label(a), strategy_key(), drain_events()     improve the report

Rules that trip people up

  • Actions are values: ints, strings, tuples or frozen dataclasses. Not lists or dicts, and not objects compared by identity. Give every action a distinct label.
  • No hidden randomness: no global random, time or uuid inside apply. Randomness after setup must be a chance node. Every game is replayed from its seed to check this.
  • Don't build legal_actions() from a set of strings, because the order changes between runs.
  • In perfect-information games, a deck shuffled in new_game is visible to the search. Model draws as chance nodes, or declare hidden information.
  • Simultaneous moves: make them sequential and hide the pending choice with determinize. Real-time games: discretize into decision points. Multi-part turns: one action per step plus "end turn".
  • Keep it to tens of actions per decision. Abstract larger action spaces.
